# Dogfood fixes round 2 (live Gemini CLI data, 2026-09-16)

Three issues seen on a real spanbox with only Gemini CLI traffic (3 traces, 5 spans, all on one UTC day).

## 1. Dashboard x-axis explodes with a single day of data (bug)

`GET /dashboard?range=24h` with data on one day: uPlot auto-scales x from 2027 to 2029 and the single point sits at the far left. Fix in `internal/web/static/app.js`: the x scale must be pinned to the selected range, not to the data. `GET /dashboard/data` already knows `from`/`to`; return them (unix seconds, `RangeFrom`, `RangeTo`) in `DashboardData` and set `scales: { x: { range: [from, to] } }` (uPlot takes a fixed `[min,max]` array or a function) for all four charts. Day buckets stay as they are. Also make single points visible: `points: { show: true, size: 6 }` on every series so one-day data renders as a dot instead of nothing. Test: extend the dashboard data test to assert `RangeFrom < RangeTo` and that `RangeTo - RangeFrom` equals 24h for `range=24h`.

## 2. Logs adapter loses the request half across batches (bug)

Gemini CLI sends the request record (`gen_ai.client.inference.operation.details` without usage) and the response record in **different** OTLP batches when the model call is slow. Observed: second span of session `e4c32829…` stored with `duration_ms = 0` and without `gen_ai.input.messages`, because pairing only looks inside one batch.

Fix in `internal/otlp/logs.go` (or a small `internal/otlp/pending.go`): keep an in-process pending map of unpaired request records keyed by `(resource session.id or service.instance.id or service.name, gen_ai.request.model)`, value = FIFO slice of `{attrs, resource, scope, timeNs, insertedAt}`. When a response record arrives, pop the oldest pending request with the same key whose time ≤ response time; merge as today. Entries older than 10 minutes are dropped on the next insert or lookup (no goroutine). Cap the map at 1000 entries total; when full drop the oldest. The map lives on the adapter struct that the web handler already owns (create one in `web.NewHandler`); it needs a mutex because ingest runs with up to 4 concurrent requests. Tests: split the existing `gemini_cli_logs.json` fixture into two requests (request record in batch A, response record in batch B) and assert the stored span has the request's start time, non-zero duration, and `gen_ai.input.messages`; a response with no pending request still stores a span with `duration_ms = 0`; expiry after 10 minutes (inject a clock function).

## 3. Trace page has no timeline (feature)

The span tree shows a relative-duration meter per row but no position in time, so a two-call session looks like two equal bars. Replace the `<meter>` in `internal/web/templates/trace.html` with a waterfall bar: a fixed-width track per row (the current last grid column, widen it to 160px on desktop, hidden under 700px as today) containing an absolutely positioned bar whose `left` and `width` are percentages of the trace's `[start_ns, end_ns]` window, computed server-side in Go (`OffsetPct`, `WidthPct` on the tree node view model, integers 0–100, minimum visible width 1%). Colour the bar with the kind accent already used for the left marker. Keep the numeric duration text. Add a thin time ruler row above the tree with 0 ms, 25 %, 50 %, 75 %, and total duration labels, computed from the same window. Percentages are numbers rendered into a `style` attribute through Go's template engine: they must be integers formatted by Go, never telemetry strings, so CSP and escaping stay intact. On the span panel show `Start offset: +N ms` next to Duration. Test: in `server_test.go` assert the trace page contains `style="left:0%;width:` for the root span and a non-zero `left:` for the child that starts later in the fixture.
